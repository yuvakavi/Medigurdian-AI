# Medical Reports

Patient reports are stored in Supabase and are accessible only through the
authenticated FastAPI routes. No report storage path, bucket URL or service-role
key is returned to the browser.

## Data and storage

| Layer | Configuration |
| --- | --- |
| Metadata table | Existing `public.medical_reports` columns: `id`, `patient_id`, `report_title`, `report_type`, `report_date`, `file_name`, `file_path`, `extracted_text`, `ai_analysis`, `status`, `created_at`, `updated_at` |
| Metadata access | The caller's Supabase JWT, so the existing owner-scoped RLS policies apply; every query also filters by the verified patient UUID |
| File bucket | Private `medical-reports` bucket, 10 MB limit, PDF/PNG/JPEG MIME types |
| File access | Server-side service-role key only, after an owner-scoped metadata lookup; the browser never receives a storage credential or public URL |
| AI analysis | Not generated by this module. `ai_explanation` is returned only when `ai_analysis` is already present in the row. |

The `report_values` table does not exist in this project, so the API returns
`values: []`. No lab values, reference ranges, diagnoses or processing progress
are invented.

## Setup

The existing project already has the table and RLS policies. If the private
bucket is missing, run:

```text
backend/migrations/20261023_medical_reports_storage.sql
```

The migration is idempotent. It creates or updates the private bucket and
re-enables RLS on `medical_reports`; it does not create, update or delete report
rows. No `storage.objects` policy is granted to `anon` or `authenticated`
because direct browser storage access is intentionally unsupported.

Required backend variables:

```text
SUPABASE_URL=...
SUPABASE_PUBLISHABLE_KEY=...
SUPABASE_SERVICE_ROLE_KEY=...
REPORT_STORAGE_BUCKET=medical-reports
REPORT_MAX_FILE_SIZE_BYTES=10485760
```

`SUPABASE_SERVICE_ROLE_KEY` is server-only. If it is absent, list/detail
requests still work, while upload, download and delete return `503`.

## API

| Method | Path | Purpose |
| --- | --- | --- |
| `POST` | `/api/reports/upload` | Multipart upload (`file`, optional `title` and `report_date`) |
| `GET` | `/api/reports/me` | The authenticated patient's reports, newest upload first |
| `GET` | `/api/reports/{id}` | Owner-scoped report metadata |
| `GET` | `/api/reports/{id}/download` | Owner-scoped file stream; add `?inline=true` for preview |
| `DELETE` | `/api/reports/{id}` | Owner-scoped delete; removes the record and private object |

Uploads are validated by extension, declared MIME type, magic bytes and size.
Object paths are generated as `{patient_uuid}/{random_uuid}.{extension}`.
Ownership checks happen before any storage read or delete. A report belonging to
another patient returns the same generic `404 Report not found.` response.

Delete resolves private storage before removing metadata. If storage is not
configured, it returns `503` and leaves the report intact. If the object removal
itself fails after the metadata delete, only a private, unreferenced object
remains; the API never exposes it.

## Frontend flow

`frontend/src/pages/Reports.jsx` supports drag-and-drop, file validation,
progress, retry, report history, details, authenticated in-app preview,
download and delete confirmation. The UI shows an explicit "no AI explanation
has been generated" state rather than placeholder analysis.
